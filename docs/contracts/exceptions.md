| Caso                                                | Respuesta               | Acción de front                                                              |
| --------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------- |
| Operación de cuenta consultada por su propietario   | `200 OperationResponse` | Leer el estado: HTTP 200 no equivale a SUCCEEDED.                            |

reconciliar la misma atención mediante la lectura exacta contratada. Sin evidencia
suficiente, mantener resultado indeterminado y revisión operativa. Esto no
introduce retención garantizada, búsqueda de operaciones perdidas ni autorización

## Cómo leer la matriz

Las respuestas funcionales indicadas suponen sesión y permisos válidos, contexto disponible, cuerpo válido y clave nueva para una intención nueva. Si falla un control HTTP previo, aplica la tabla de HTTP, no el resultado funcional posterior al `202`.

`REJECTED` describe el resultado de un comando; no significa que se haya rechazado el ingreso del alumno. Un rechazo de ingreso aplicado es una operación `SUCCEEDED` cuya ejecución termina `ENTRY_REJECTED`.

Todos los paths de este documento usan el prefijo `/api/v1`. `E` significa el `washExecutionId` conservado al seleccionar la atención; `A`, su `appointmentId`. Las versiones de cita y ejecución son independientes. La llegada crea/recupera contexto desde `appointmentId`; su DTO no contiene `expectedVersion`.

## 2. Dos supervisores y solicitudes distintas

Usar una clave aleatoria nueva por intención; dos supervisores no deben compartir una clave fija. El BFF separa el ámbito por cuenta/operación pública/clave, mientras que el owner deduplica por productor/comando/clave. Una colisión entre cuentas puede terminar como `REJECTED/IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_REQUEST`; no confundirla con una carrera de versión.

Dos cierres distintos con la misma versión inicial no se convierten en dos éxitos: el ganador aplica; el perdedor debe releer. Con versión obsoleta, el resultado funcional es `VERSION_CONFLICT`. Si se envía otra clave con la versión actual de una ejecución ya completada, `/complete` comprueba primero la asignación y normalmente devuelve `ACTIVE_RESOURCE_ASSIGNMENT_NOT_FOUND`, porque ya fue liberada. No existe un contrato de “ya completado equivale a éxito” para una intención distinta.

La repetición exacta de una intención conserva su operación. La deduplicación puede republicar un Result técnico al reentregar un mensaje; no crea otra transición ni otro evento de negocio del cierre. La entrega de mensajes no debe interpretarse como entrega única física.

La comparación definitiva del supervisor usa `GET /wash/supervision/executions/E`. No consultar la operación de otro supervisor: `GET /operations/{operationId}` sólo permite ver las operaciones de la misma cuenta y devuelve `404` vacío si no son visibles.

El runtime devuelve `404` vacío para operaciones inexistentes o no visibles. La corrección explícita de OpenAPI está en [backend PR #167](https://github.com/AnthonyNav/estoma-services/pull/167), pendiente de integración y despliegue; no sustituye todavía el snapshot desplegado. Front debe tolerar ese cuerpo vacío y no interpretarlo como ausencia de efectos.

La ruta admite operaciones anónimas: omitir Bearer puede ocultar como `404` una operación de cuenta. Un Bearer inválido o revocado devuelve `401 Problem`. Recuperar el contexto de la cuenta original y consultar el mismo `pollPath`; conservar ID, clave y solicitud original. Si la operación sigue sin estar disponible, reconciliar la atención exacta y mostrar resultado indeterminado cuando no se pueda resolver. No generar otra clave ni reenviar automáticamente el comando.

| Competencia                     | Versión obsoleta ya visible al leer                                                                             | Carrera real entre ambas lecturas/escrituras                                                                                                                                                                                                                                                                                                                        |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Aprobación y rechazo de ingreso | `REJECTED/VERSION_CONFLICT`; con versión actual pero decisión previa/estado incompatible, `INVALID_ENTRY_STATE` | **Hueco confirmado:** ambas pueden pasar la lectura inicial e intentar insertar `entry_validations` antes del CAS. La restricción única evita dos decisiones, pero la excepción de duplicado no se clasifica para reintento; puede ir a DLQ y dejar la operación BFF sin Result. No prometer siempre `VERSION_CONFLICT` en esta carrera hasta corregirla y probarla |
| Reasignaciones distintas        | `VERSION_CONFLICT`; con versión actual y estado ya resuelto, `WASH_EXECUTION_NOT_PENDING_REASSIGNMENT`          | Locks de recursos/asignación y CAS protegen la transición; con el manejo optimista de PR163, el perdedor del CAS revierte y se reentrega para resolver versión. La confirmación viva de este escenario sigue pendiente                                                                                                                                              |
| Cierres distintos               | `VERSION_CONFLICT`; versión terminal actual suele producir `ACTIVE_RESOURCE_ASSIGNMENT_NOT_FOUND`               | La reentrega de la misma intención no duplica cierre/liberación. Las carreras probadas de PR163 cubren envío del alumno frente a cierre directo; no deben etiquetarse como fixture de dos supervisores si no se ejecutó ese escenario                                                                                                                               |

La restricción única y la transacción protegen contra duplicar la decisión de ingreso, pero esa protección no equivale a entregar un resultado útil al cliente. La corrección de aprobación/rechazo ya está implementada localmente: ejecuta el CAS antes de insertar la validación, con regresiones deterministas aprobadas para aprobación/rechazo y dos rechazos. Está publicada en [PR165](https://github.com/AnthonyNav/estoma-services/pull/165), integrado como `e9704201` tras review favorable y CI verde, con 109 pruebas aprobadas y una omitida; despliegue owner `e970420` comprobado; falta prueba autenticada; mientras tanto front conserva la operación y muestra pendiente de reconciliación, sin inventar un error funcional para un Result que no llegó.

## 3. HTTP inmediato y operación incierta

Esta garantía se refiere al intento que produjo la respuesta. **No prueba que una solicitud anterior con esa clave no haya sido aceptada.**

| Respuesta del POST                                                                           | ¿Creó una operación nueva ese intento?                                              | Acción de front                                                                                                                      |
| -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `400 BFF.INVALID_REQUEST` del BFF: JSON, DTO, cantidades, UUID, versión o cabecera inválidos | No: validación antes de aceptar o rollback de la transacción                        | Corregir datos. Si existía otra intención incierta, reconciliarla por separado                                                       |
| `401 BFF.AUTHENTICATION_REQUIRED` / `BFF.AUTHENTICATION_INVALID`                             | No para ese intento                                                                 | Recuperar sesión; conservar recibo e intención anterior                                                                              |
| `403 BFF.ACCESS_DENIED`                                                                      | No para ese intento                                                                 | No repetir a ciegas; puede haber cambiado el acceso o faltar la relación de propiedad proyectada                                     |
| `409 BFF.IDEMPOTENCY_CONFLICT`                                                               | No otra operación; existe una intención previa con esa clave y distinto fingerprint | Recuperar la intención original, no sustituirle el cuerpo                                                                            |
| `503 BFF.PROJECTION_UNAVAILABLE` emitido por los controles locales previos al POST de Lavado | No para ese intento                                                                 | Esperar contexto y reintentar la misma intención si sigue siendo válida                                                              |
| `503 BFF.WASH_UNCLASSIFIED_ENTRY_REJECTION_UNAVAILABLE`                                      | No: gate previo a `/entry-decision`                                                 | Capacidad apagada; no enviar `false/false` para fingir evaluaciones                                                                  |
| `202` con recibo válido                                                                      | Sí hay una operación durable, nueva o recuperada por idempotencia                   | Guardar recibo y consultar operación                                                                                                 |
| Timeout, desconexión, CORS, respuesta perdida, `5xx` genérico o error de proxy               | Ambiguo                                                                             | Consultar el recibo conocido o repetir exactamente la intención retenida; nunca generar otra clave automáticamente                   |
| `429` de un intermediario                                                                    | Sin garantía específica de este contrato                                            | Respetar `Retry-After` si existe y reconciliar; el código BFF revisado no define rate limiter ni un Problem de Lavado para este caso |

La disponibilidad de horarios tiene además un `503` que agenda una consulta de refresco; no crea una **operación de comando** del alumno. No extrapolar que todo `503` de cualquier ruta carece de efectos internos.

### Retención y reintento

- Idempotencia: el registro nace sin caducidad mientras la operación está `PENDING`. Al terminalizar se fija `expires_at = terminalAt + BFF_IDEMPOTENCY_RETENTION_HOURS`, valor predeterminado y mínimo admitido de **24 horas**. Repetir el Result no desplaza una expiración ya fijada.
- Operaciones: existe `BFF_OPERATION_RETENTION_DAYS=7` como configuración predeterminada, pero el código revisado no conecta ese valor a una purga ni establece `ClientOperation.expiresAt` al terminalizar. **No está certificado un TTL operativo efectivo de siete días ni un borrado automático al cumplirlo.** Falta confirmar política/ejecutor del entorno antes de ofrecer ese plazo como garantía al usuario.
- La consulta de la clave existente no descarta registros sólo porque su `expires_at` ya pasó. Mientras ambos registros sigan presentes, el reintento devuelve la operación original; la ventana mínima prevista no autoriza reutilizar claves después de 24 horas.
- La misma intención se recupera con la misma cuenta, operación pública, clave y cuerpo canónico; conservar también ruta e identificador. La autenticación, permisos y controles previos vuelven a aplicarse al POST. Una pérdida de acceso puede impedir recuperar el recibo mediante POST aunque la operación anterior exista.
- No existe endpoint público de listado de operaciones por usuario, búsqueda por clave o recuperación por `appointmentId`. Si se conserva clave/cuerpo pero no recibo, repetir exactamente permite recuperar éste mientras se retenga la deduplicación. Sin esas referencias, o tras su eliminación, hace falta intervención operativa; no fabricar una solicitud nueva.

### `FAILED`, `EXPIRED` y `PENDING` prolongado

No equivalen a ausencia de efectos. Conservar operación, ejecución/cita e intención; consultar operación y lectura exacta. Si la lectura muestra el resultado de la misma atención, presentarlo sin repetir el comando. Si falta contexto, llega `404/503`, hay contradicción o la ejecución aún no avanzó, mantener “resultado pendiente de comprobar” y solicitar revisión operativa al agotar el presupuesto de seguimiento. Una lectura atrasada no autoriza otra intención.

El código revisado no convierte automáticamente un timeout de front en `EXPIRED`. El agotamiento de publicación puede dejar un Outbox fallido y la operación `PENDING`; tampoco implica por sí mismo `FAILED` público. No inventar un plazo de expiración del comando a partir del timeout visual.

Sólo crear otra intención cuando exista un rechazo definitivo compatible con la lectura actual, o una reconciliación que descarte efectos pendientes, y el usuario confirme de nuevo una acción que todavía está permitida. `FAILED/EXPIRED` por sí solos no satisfacen esa condición.

## 4. Operación aplicada y lectura atrasada

Después de `SUCCEEDED` puede observarse un `200` con la versión/estado anterior, `503 BFF.PROJECTION_UNAVAILABLE` por contexto incompleto o contradictorio, Home sin la cita seleccionada, o lookup `404 BFF.WASH_ENTRY_NOT_FOUND` cuando ya no hay atención activa para esa búsqueda/fecha. La lectura exacta puede devolver `404 BFF.WASH_EXECUTION_NOT_FOUND` si todavía no está proyectada. Ninguno de esos casos convierte un éxito en un rechazo.

| Acción confirmada                                   | Campos que deben coincidir después de converger                                                                                                                                                                 |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Llegada                                             | Mismo A; obtener y conservar E real, ejecución `PENDING_ENTRY`, `arrivedAt` y versión de ejecución. No inventar E desde la tarjeta                                                                              |
| Aprobación con asignación                           | Mismos A/E, versión de ejecución posterior, `IN_PROGRESS`, asignación activa completa y cita `IN_PROGRESS`                                                                                                      |
| Aprobación sin recursos                             | Mismos A/E, versión posterior y `PENDING_REASSIGNMENT`; mostrar falta de recursos, no cabina inventada ni aprobación con espacio                                                                                |
| Rechazo de ingreso aplicado                         | Mismos A/E, ejecución y cita `ENTRY_REJECTED`, `rejectionReason`, sin asignación activa                                                                                                                         |
| Reasignación                                        | Mismos A/E, versión posterior, `IN_PROGRESS`, asignación activa con los IDs de cabina/tina elegidos; refrescar lista de pendientes                                                                              |
| Cancelación clínica                                 | Mismos A/E, ejecución y cita `CANCELLED`, asignación activa null; última asignación si existió. El DTO actual no expone motivo/tipo/fecha de cancelación clínica                                                |
| Cierre                                              | Mismos A/E, ejecución y cita `COMPLETED`, versión posterior, `completedAt`, finales exactos, activa null y última asignación. Originales preservados si hubo envío; null si no lo hubo                          |
| Cancelación del alumno o inasistencia sin ejecución | Mismo A si Home aún lo selecciona; `CANCELLED` o `MISSED`. Sin E no puede usarse lectura exacta de ejecución; falta una lectura pública histórica por appointmentId para reconciliar independientemente de Home |

En exacta, `washExecution.version` y `washExecution.executionVersion` son alias y deben coincidir; no compararlos con `appointment.appointmentVersion`. Los IDs de recurso están anidados como `cabin.resourceId`/`tank.resourceId` en supervisión y planos como `cabinId`/`tankId` en Home. `nextAction` y futura `canComplete` orientan la UI; no sustituyen la validación del comando.

Recomendación de consumo, **no SLA medido**: polling inicial cada 1 s, después cada 2–5 s con backoff; suspender la consulta periódica de pantallas ocultas, conservar el recibo y permitir reanudar. Respetar `Retry-After` cuando exista. No está garantizado en Home, lookup, exacta ni operaciones; el handler lo entrega explícitamente en el refresco de disponibilidad de horarios.

No hay tiempo backend certificado para concluir “no se aplicó” ni un umbral global implementado de “requiere revisión”. Front puede acotar su espera visual y ofrecer revisión/reanudación al agotarla, pero ese presupuesto no cambia el estado del comando ni habilita otro intento.

**Llegada frente a inasistencia:** la evaluación interna bloquea/relee la cita, verifica versión, tolerancia, autorización, calidad de proyección, eventos causales pendientes y confirmación de ejecución. Una llegada válida confirmada impide marcar la inasistencia; la evidencia fuera de ventana no la protege. `DEFERRED` y sus códigos de evaluación interna no son estados públicos de `OperationResponse` que front deba interpretar como resultado de su POST. Si una llegada pública fue aceptada con `202`, se sigue su operación; no se declara ganadora por haber abierto la pantalla antes que el scheduler.

**Elegibilidad del mismo día:** consultar `GET /wash/appointments/availability` con los filtros del contrato de agendamiento. Devuelve `canSchedule`, `blockingReasons`, `dailyPenaltyPoints`, `dailyCompletedAppointments`, contexto de autorización excepcional y horarios. Rechazo de ingreso y cancelación clínica suman cero puntos; inasistencia y cancelación del alumno suman uno. La política actual bloquea con tres puntos, limita a dos citas completadas por día y exige autorización excepcional después de una completada. Una autorización utilizada se libera por cancelación clínica, no por rechazo, inasistencia o cancelación del alumno. Front muestra el resultado owner; no recalcula esos permisos ni supone que cero puntos asegure un horario disponible.

**Motivos y acciones públicas:** `rejectionReason` sí está en Home/lookup/exacta. Los DTO actuales no contienen `cancellationType`, `cancellationSubreason`, `cancellationReason` ni `cancelledAt`. La información existe internamente, pero no se puede presentar como dato confirmado por una lectura pública. Su exposición es un pendiente de backend. No atribuir una cancelación al alumno o a la clínica sólo por ver `CANCELLED`.

**QR:** las citas terminales no ofrecen QR utilizable (`qrUsageContext=NONE`, representación nula en Home). Con lectura QR habilitada, una representación desconocida/revocada responde `404 BFF.WASH_ENTRY_NOT_FOUND`; un mapping incoherente, futuro o todavía asociado a una vista terminal puede producir `503 BFF.PROJECTION_UNAVAILABLE` hasta reconciliarse. La capacidad apagada o no preparada también devuelve `503`; no significa “QR inválido”. Una copia ocultada por UI durante `IN_PROGRESS` no se revoca automáticamente. La vigencia real requiere fecha y proyecciones coherentes; no hay un QR vivo certificado en estos ejemplos.

## 6. Pérdida de recursos y reasignación

| Estado / acción                                                 | Operación y resultado                                                                                                                                                                                       | Qué debe mostrar o refrescar front                                                                                                                                                             |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deshabilitar recurso con E `IN_PROGRESS`                        | `POST /wash/operational-resources/disable`, supervisor, exactamente cabina o tina y causa. La ejecución afectada pasa a `PENDING_REASSIGNMENT` y conserva la asignación anterior mientras se resuelve       | Mostrar pendiente, no continuidad del lavado por conservar una asignación. Home no ofrece QR de uso; lookup indica `REASSIGNMENT`. Refrescar E y `GET /wash/supervision/pending-reassignments` |
| Deshabilitar durante `EXIT_SUBMITTED`                           | El código actual **no cambia** esta ejecución a pendiente. Conserva envío y asignación; `/complete` sigue admitiendo cierre normal                                                                          | Seguir mostrando revisión de salida. Si producto requiere reasignar también en este estado, hace falta otra transición; no está implementada                                                   |
| Alumno envía desde `PENDING_REASSIGNMENT`                       | `/exit` con versión actual y propiedad válida: `202` → `REJECTED/INVALID_WASH_EXECUTION_STATUS`                                                                                                             | Resolver primero el contexto pendiente; no inventar un envío diferido                                                                                                                          |
| Supervisor completa desde `PENDING_REASSIGNMENT`                | No permitido. Con asignación anterior activa: `REJECTED/INVALID_WASH_EXECUTION_STATUS`; sin asignación: `REJECTED/ACTIVE_RESOURCE_ASSIGNMENT_NOT_FOUND`. Con versión obsoleta gana antes `VERSION_CONFLICT` | No habilitar cierre por la presencia aislada de materiales o recursos históricos. Resolver reasignación o cancelación clínica                                                                  |
| Candidatos disponibles                                          | `GET /wash/supervision/pending-reassignments/E/candidates`: `200`, snapshot para la misma versión de E                                                                                                      | Cada candidato es una pareja válida. No combinar cabina de una fila y tina de otra; consultar no reserva                                                                                       |
| Sin candidatos confirmado                                       | Mismo GET: `200`, `candidates=[]`, recomendación null                                                                                                                                                       | Mostrar sin recursos. Refrescar o, con intención del supervisor, solicitar cancelación clínica; owner vuelve a comprobar `CAPACITY_LOSS`                                                       |
| Aún no se puede saber                                           | Mismo GET: `503 BFF.PROJECTION_UNAVAILABLE` por gate, falta/stale del snapshot, versión distinta o ejecución ya no pendiente                                                                                | Refrescar E y lista. No mostrar “cero recursos confirmado” ni cancelar automáticamente                                                                                                         |
| Pareja pierde capacidad al confirmar                            | `POST /wash/executions/E/reassignment`: `202` → `REJECTED/TANK_CAPACITY_EXHAUSTED`                                                                                                                          | Refrescar E, pendientes y candidatos; nueva elección y confirmación deliberada con clave nueva                                                                                                 |
| Recurso quedó inactivo, indisponible, en limpieza o bajo cierre | Mismo POST: `REJECTED/RESOURCE_NOT_AVAILABLE`                                                                                                                                                               | Mismo refresco. No repetir indefinidamente la selección anterior                                                                                                                               |
| Pareja inválida / contexto ausente                              | `INVALID_RESOURCE_COMBINATION`, `RESOURCE_CONFIGURATION_UNAVAILABLE` o `APPOINTMENT_CONTEXT_UNAVAILABLE`                                                                                                    | Corregir elección sólo para pareja inválida; para proyección ausente, esperar recuperación                                                                                                     |
| Otra acción resolvió la ejecución                               | Versión vieja: `VERSION_CONFLICT`; versión actual pero ya no pendiente: `WASH_EXECUTION_NOT_PENDING_REASSIGNMENT`                                                                                           | Leer E exacta y presentar lo que ocurrió; no tratarlo automáticamente como éxito de esta selección                                                                                             |

El snapshot de candidatos dura **10 segundos** y se liga a la versión de ejecución. Su flag es `BFF_WASH_REASSIGNMENT_CANDIDATES_ENABLED`. El tiempo de snapshot no reserva capacidad ni establece cuánto debe esperar la pantalla.

Al reasignar una ejecución iniciada se libera la asignación anterior, se crea otra y E vuelve a `IN_PROGRESS`. Después de converger debe desaparecer del listado de pendientes; temporalmente puede seguir visible. Restaurar un recurso no reasigna ni reactiva por sí mismo una ejecución pendiente.

**Liberación no equivale a disponibilidad:** `activeResourceAssignment=null` confirma que esa ejecución ya no ocupa la asignación. Una cita `IMMUNOCOMPROMISED` con uso físico puede iniciar limpieza; el recurso puede seguir indisponible por limpieza, deshabilitación, cierre u otras asignaciones. Usar candidatos/disponibilidad owner, nunca calcular cupo sólo restando una tarjeta completada. Los DTO de ejecución no entregan un indicador público completo de “este recurso ya se puede usar” ni todo su periodo de limpieza.

## 7. Evidencia y fixtures

Los [13 ejemplos JSON](examples/wash-exceptions.examples.json) son **respuestas sintéticas para pruebas del adaptador**, no credenciales, citas vigentes ni capturas del entorno. Doce cuerpos se contrastaron con el esquema OpenAPI desplegado `a44b8b5`, incluyendo `canComplete` en lecturas exactas; el caso restante reproduce el `404` vacío de operaciones observado en código, que difiere del Problem anunciado por ese snapshot. Para cada caso aplicar el contrato HTTP común, después el `errorCode`/estado de su fila y las reglas de relectura. No derivar un endpoint nuevo de un identificador de escenario.

| Caso                                              | Evidencia disponible                                                                                                 | Fixture/ejecución pendiente                                                                                            |
